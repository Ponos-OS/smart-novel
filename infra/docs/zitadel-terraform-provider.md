# Configure ZITADEL with Terraform (Future Enhancement)

Not part of the compose-to-kind feature. Revisit after it ships.

## Context

`modules/zitadel` runs ZITADEL itself. `modules/zitadel_setup` runs `local-setup/setup-zitadel` (JavaScript) as a Kubernetes Job. The script creates the project, roles, OIDC applications, test users, the self-registration action and impersonation, and writes the PATs, client IDs and user IDs to files on the `zitadel-credentials` volume.

`local-setup/setup-zitadel/Dockerfile` exists only to package that script as an image, because a Job cannot bind-mount the folder.

## Idea

Replace the script with the `zitadel/zitadel` Terraform provider, so ZITADEL's configuration is Terraform resources like everything else. The `zitadel_setup` module and the Dockerfile would go away, and `modules/zitadel` stays as it is.

## Things to Plan For

- Provider authentication: the provider needs a reachable ZITADEL and a token or key while Terraform runs. The bot PAT is generated by ZITADEL on its first start, so it does not exist at plan time. Expect two applies: one for ZITADEL, and a second for its configuration, as a separate root module or stage.
- Reachability: Terraform must reach ZITADEL from where it runs. Locally `localhost:8080` works. In a cloud environment it needs network access to the cluster, or a publicly served ZITADEL.
- Coverage: check that the provider covers everything the script does before committing to it. Unverified: impersonation and the security policy, token exchange for the e2e bot, the post-self-registration action, and machine user keys and PATs.
- Outputs instead of files: the script writes the client ID, user IDs, bot key and PATs to files that the apps and the e2e suites read (Step 8 copies them to `local-setup/{pats,client,user-ids}`). With Terraform these would become outputs, so the consumers and the e2e global setup need to change with it.
- Test users are dev and e2e only. The production configuration would likely be a trimmed version of the dev one, with generated passwords.

## Decision

Keep the JS script for now. It works and matches what the e2e suites expect. Convert later, in its own feature.
