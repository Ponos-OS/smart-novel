## Decisions already made

- Backend: Go with [ent](https://entgo.io) and `entgql` (gqlgen underneath). Ent replaces Prisma.
- Task runner: [Taskfile](https://taskfile.dev) replaces Nx. `task` is a system tool, never an npm dependency: installed with apt on developer machines, with `go-task/setup-task` in CI and with the official install script (pinned release) in Docker images. Scripts and docs call `task`, never `npx task`. Nx, `project.json`, `nx.json` and every `@nx/*` dependency go away.
- `libs/shared` goes away. Rules both apps need live in one JSON spec; the constants for each language are generated from it. The small helper functions are copied by hand into each language.
- Anything a task can regenerate is git-ignored and never committed: generated shared constants, ent code, gqlgen code, the GraphQL schema, frontend GraphQL types. Docker builds, CI and `task` dependencies must run generation first.
- `APP_ENV` (`development`, `production`, `test`) replaces `NODE_ENV` as the backend's own setting, including the Go backend. `NODE_ENV` stays only where Node libraries read it (the frontend Dockerfile, Vite, Vitest, and the interim NestJS production image, where Apollo turns off introspection and stack traces when it is `production`).
- The frontend stays TypeScript/React/Vite; only its tooling changes.
- The Go API keeps Relay Global Object Identification: the `Node` interface with `Query.node(id)` and `Query.nodes(ids)`, resolved through ent's `Noder`. Do not drop it.
- `apps/backend-e2e` and `apps/frontend-e2e` stay TypeScript. The backend e2e suite talks to the API over HTTP only, so it is the parity oracle for the port: the Go backend is done when that suite passes against it.

## Project layout

Go modules are tied together by a root `go.work`; the frontend and e2e projects stay plain npm projects. The Go layout follows the ent/entgql/gqlgen conventions (`ent/schema`, `ent/entc.go`, `ent/generate.go`, `gqlgen.yml`) and the usual `cmd/` + `internal/` split.

```
Taskfile.yml                    root tasks, includes the per-app Taskfiles
go.work                         use ./apps/backend ./tools
tools/                          its own Go module
  gensdl/                       reads the limits of apps/backend/api/*.graphql, writes the TS constants (step 7a-2)
apps/
  backend/                      Go module (go.mod, Taskfile.yml, gqlgen.yml, Dockerfile, .air.toml, .golangci.yml)
    cmd/server/main.go          wiring only: config, dependencies, run
    api/
      *.graphql                 only what ent cannot derive: custom queries/mutations, computed or viewer fields (committed)
      ent.graphql               generated by entgql (ignored)
    ent/
      schema/*.go               one file per entity (committed)
      entc/main.go              entgql extension, run by `go generate` from the module's generate.go (committed)
      migrate/migrations/       versioned Atlas SQL (committed)
      *                         everything else generated (ignored)
    internal/
      config/                   env parsing
      server/                   HTTP router, middleware, health, GraphQL handler
      graph/                    gqlgen resolvers, thin: authorize, call a service, map errors
        generated.go, model/    generated (ignored)
      auth/                     ZITADEL JWT, viewer in context, authorization functions
      <domain>/                 novel, chapter, tag, writer, license, stats, ...: services and business rules
      platform/                 adapters: redis, objectstorage, rabbitmq, beatrice, fithara, otel
      shared/                   generated constants (ignored) and hand-written helpers
  frontend/                     Vite app; src/generated/ ignored
  backend-e2e/                  vitest, HTTP only
  frontend-e2e/                 Cypress
  backend-nest/                 the old NestJS app, kept as a reference until step 11, not built
infra/                          terraform, scripts, observability
.github/
```

Rules:

- A domain package never imports `internal/graph` or `internal/server`; resolvers import domain packages. Domain packages talk to the outside world through interfaces they own, implemented in `internal/platform`.
- The API schema is generated from the ent schema, not written by hand: entgql (`WithSchemaGenerator`, `WithSchemaPath("../api/ent.graphql")`, `WithWhereInputs(true)`, `WithConfigPath`, `entgql.Mutations(...)`, `entgql.OrderField`, `entgql.RelayConnection`) emits the entity types, enums, connections, ordering, filters and create/update inputs. Hand-written files in `apps/backend/api` only `extend` it with operations that are not entity CRUD and with computed or viewer-specific fields such as `Chapter.isRead`. `gqlgen.yml` and the frontend codegen both read `apps/backend/api/*.graphql`.
- Ent schema files hold fields, edges, indexes, validators and `entgql` annotations only; business rules go in the domain package.
- Tests sit next to the code (`*_test.go`), table-driven. Anything that needs a real PostgreSQL is covered by `backend-e2e`; there are no Docker-based Go integration tests.

Built as (decisions and deviations from the bullets above; steps 6 to 8 start from this):

- Spike, written up: (a) the `zitadel-go` gRPC client reached ZITADEL through the kind ingress with a PAT (`UserServiceV2.ListUsers`, HTTP/2 end to end, `auth.localhost:8080` from the host); inside the cluster `auth.localhost` resolves to the pod itself, so step 7 dials `traefik:80` with the issuer as the authority, the way `internal/auth/zitadel.go` does for HTTP. (b) Introspection against local verification: the access tokens the e2e fixtures get are JWTs with the roles but without email or name, so local verification needs a second call (userinfo, cached in Redis, as the NestJS provider did) and sees a revoked token only after that cache expires; introspection with an API application returns the roles, email, name and `active` in one call. Chosen: introspection through `zitadel-go` (`oauth.NewIntrospectionVerificationWithCache`), cached in memory for 30 s (and never past the token's own expiry), keyed by the hash of the token. The cost is one call per distinct token per 30 s and credentials for an API application.
- `zitadel_config` creates that API application (`zitadel_application_api.backend`, basic authentication) and outputs its client ID and secret; `local/1-app` and `hetzner` pass them as `ZITADEL_INTROSPECTION_CLIENT_ID` and `ZITADEL_INTROSPECTION_CLIENT_SECRET` (the second goes to a Secret). The Go backend also needs `ZITADEL_ISSUER_URL` (the `iss` of the tokens) and `ZITADEL_INTERNAL_URL` (where it reaches ZITADEL; requests keep the issuer's host, because ZITADEL picks its instance by host).
- Not ported: the NestJS fallback that asked ZITADEL for the roles of a token whose userinfo had none (PATs). A token without roles is a user without a role. `ZITADEL_PROJECT_ID`, `ZITADEL_CLIENT_ID` and the PATs are not read by the Go backend yet; the management client of step 7 uses the PATs.
- `auth.Middleware` verifies a bearer token if there is one and never rejects: a rejected token only matters to a protected operation, a public one ignores it, as before. `auth.Guard` is a gqlgen field middleware that protects every root field by default (`UNAUTHENTICATED` with the same message as before, "Missing Bearer token in Authorization header" or "Invalid or expired token"); `@public` opens a field and `@hasRole(role: writer)` asks for a role or higher (`FORBIDDEN`). The directives are markers: `Guard` is the one place that enforces them. The codes `UNAUTHENTICATED` and `FORBIDDEN` are in `spec/shared.json`.
- The permission rules are one function, `auth.Can(viewer, action, resource)` in `internal/auth/authz.go`, with typed resources (`Novel`, `Chapter`, `License`; a sealed interface, so nothing else compiles), admins allowed first and anything unlisted denied; covered for every role and ownership combination. The service that has the owner's user ID calls them in steps 6 and 7; reading needs only a viewer. ent has no roles of its own; it has hooks and a privacy policy engine, and neither is used: a rule that needs the owner of the novel needs a database lookup, which a privacy policy in `ent/schema` can only do through the generated `ent/privacy` and `ent` packages, and generating the code needs the schema package to compile first. The service already loads the novel it changes, so calling the functions there costs no extra query and tests without a database. Revisit if the rules multiply (a hook registered on the client in `database.Open` would enforce them at the data layer without that problem).
- `whoAmI` is ported (`api/auth.graphql`), `health` is `@public`, and the query depth limit of 7 is `depthLimit` in `internal/server/depth.go`, counted the way `graphql-depth-limit` counted it.
- Verified against the Go backend with the existing `backend-e2e` specs: see the log entry.
- Audience, found at the end of the step and fixed: a token requested with the frontend's scopes only had ZITADEL's own project in `aud`, and introspection by our API application answered `active: false`; the e2e fixtures hid it because they request `urn:zitadel:iam:org:project:id:<project>:aud`. The frontend now adds that scope itself (`main.tsx` appends it to `VITE_OIDC_SCOPE`), so the audience is a real check. The project ID reaches the frontend like the client ID: `VITE_OIDC_PROJECT_ID` from terraform (`local/1-app`, `hetzner`) in dev, and a build-time placeholder (`__OIDC_PROJECT_ID_PLACEHOLDER__`) replaced by the start scripts in the e2e and Hetzner images. Verified on the real stack: tokens with the frontend's scopes plus that audience give `whoAmI` for writer, admin and user, and the dev frontend serves the composed scope. Not run: the placeholder replacement in a built image (the same mechanism as the client ID) and a real browser login (needs the frontend operations of step 9).
- Malformed IDs are answered `BAD_REQUEST` ("Invalid ID", `internal/graph/scalar`), the code the cursor errors already use; as for every resolver error the HTTP status stays 200.

Built as (decisions and deviations from the bullets above; steps 7 to 9 start from this):

- **Contract: the entgql shape, chosen by the user for this step.** The `backend-e2e` specs were ported to it instead of the Go API copying the NestJS one. What the frontend (step 9) and any client must absorb, on top of the list in step 4:
  - `tagsConnection(filters)` is `tags(where: TagWhereInput)`. `filters.statuses` is `where.statusIn`, and the "name or a word in it starts with" search is `where: {or: [{nameHasPrefix: t}, {nameContains: " t"}, {nameContains: "-t"}]}`. Readers always get approved tags only; an admin gets approved ones unless `where` names a status.
  - `novelsConnection(filters, orderBy)` is `novels(where: NovelWhereInput, orderBy: NovelOrder, chapterCount: ChapterCountRangeInput, ownerIds: [String!])`. A tag filter is `hasTagsWith: [{nameIn: [...]}]` and `not: {hasTagsWith: ...}`; the first chapter date range is `firstChapterCreatedAtGTE/LTE`; `state` is `where.state`. `chapterCount` and `ownerIds` stay arguments because ent's where input cannot express a count or a writer by identity-provider ID. `ownerIds` and the other identity-provider IDs (`NovelWriter.userId`, `Tag.requesterUserId`) are `String`, not `ID`: they are not UUIDs. The "to before from" refusal is gone for novels (kept for `statsSnapshots`). A NUL character in any argument is still a `BAD_REQUEST` (`rejectNUL` in `internal/server`, which also covers the tag names; NestJS only checked the novel tag filter).
  - `Novel.chaptersConnection(orderBy, filters)` is `Novel.chapters(orderBy, where)`: CHAPTER_NUMBER ascending by default, a page of 100 by default and at most (it was unbounded). `totalCount` is entgql's. `statsSnapshotsConnection(filters: {from, to})` is `statsSnapshots(where: {dayGTE, dayLTE})`, the UTC day of each bound.
  - `Novel.tags` is `[Tag!]`, not `[String!]!`. Field names follow ent: `novelID`, `contentID`, `narrationURL`, `coverURL`, `licenseID`. Timestamps are `Time` (RFC 3339), including the arguments `expectedUpdatedAt` and `expectedContentUpdatedAt`. `Novel.license` comes with the `license` edge.
  - Cursors are ent's: unsigned, not tied to a filter or an order, and `after` with `before` is allowed (a range). A cursor ent did not make is the error code `INVALID_CURSOR` with the message "Invalid cursor" (the `Cursor` scalar in `internal/graph/scalar`; step 7a-2 gave it its own code, it was `BAD_REQUEST`). `CURSOR_SIGNING_SECRET` is not needed and step 9 removes it.
  - **GraphQL names follow Go names, initialisms capitalized** (`novelID`, `chapterIDs`, `ownerIDs`, `userID`, `requesterUserID`), because entgql derives its names from the ent field (`novel_id` becomes `novelID`) and cannot rename them; the hand-written schema matches so the API does not mix spellings. The NestJS spellings (`novelId`, `chapterIds`, `ownerIds`, `userId`, `requesterUserId`) are renames the frontend absorbs in step 9. Do not rename generated output to fight this.
  - `Query.node` and `nodes` (Relay Global Object Identification) are kept, by the user's decision, and must work: they resolve any entity from its ID through ent's `Noder` (`client.Noder`), with the same visibility and exposure rules as the typed fields. Today they are stubs that answer null; implementing them is scheduled for step 9.
- **Ordering by FIRST_CHAPTER_CREATED_AT is hand-written** (`novel.PageByFirstChapter`): ent's cursor on a NULL date falls back to the ID alone and loses its place at the border between novels with and without a chapter, and the contract says the ones without come last in both directions. The keyset conditions are unit-tested as SQL, and the e2e spec pages both directions across the border. It does not eager-load edges; `license` and `tags` load per row on that order only.
- **The API exposes what NestJS exposed and no more.** entgql would also have published `Writer` (the generated `Novel.writer: Writer!` handed out every writer's email), `Tag.requester_user_id`, `Tag.novels`, `Chapter.novel`, `Novel.licenseID`, `License.textHash`, `License.isDraft`, `License.novels` and `StatsSnapshot.createdAt`. - **Input is cleaned, not only checked:** `validation.SingleLine` (names, titles, tag names: control characters including NUL, invisible spaces and invalid UTF-8 removed, every white space a single space, trimmed) and `validation.Text` (descriptions and chapters: the same except line breaks and tabs stay, line breaks are `\n`) run as the `@isString` directive before the rules (one line by default, `multiline: true` for descriptions and chapters), so a name made of invisible characters is blank. - **Input rules are schema directives, on every input and argument with a text or list rule.** `api/validation.graphql` declares `@isString(multiline, allowEmpty, message)` (cleans, refuses a NUL, and refuses blank unless `allowEmpty`; the three directives it replaced differed in exactly those three ways, so they are its two arguments), `@minLength(min)`, `@pattern(regex)`, `@maxLength(max)` (the four with an optional `message`, which the bad request then carries instead of the generic "Invalid input") and `@maxSize(max)` (`INPUT_FIELD_DEFINITION | ARGUMENT_DEFINITION`), implemented in `internal/graph/directives.go`; they run while gqlgen reads the argument, in the order written (`name: String! @isString @maxLength(max: 50)`: clean, then check), on a string, an optional string (absent passes) and a list of strings. The `Normalize` methods of the tag, novel and chapter inputs, `NormalizeContent` and the batch-size check of `MarkRead` are gone. Consequences: (1) accepted by the user: gqlgen stops at the first failing field, so a client gets one violation per request instead of all of them; (2) decided by the user: gqlgen reads arguments before `auth.Guard` runs, and that stays, so invalid input is answered `BAD_REQUEST` before the caller's identity or role is looked at, even for an anonymous caller (the data is known to be usable before anything else runs); IDs need no directive, since the `ID` scalar (`scalar.UUID`) refuses a value that is not a UUID with `BAD_REQUEST` "Invalid ID"; (3) `@isString` refuses a NUL itself (cleaning would drop it before `rejectNUL` sees it); (4) the limits (50, 650, 100) are literals in the schema while `spec/shared.json` still holds them for the ent schema, until the shared constants go; (5) `@minSize` and other rules are added when needed. ### Step 8b: Object storage and covers

### Step 8c-2: The callbacks Beatrice makes

`POST /beatrice-callbacks/gen-upload-url` and `POST /beatrice-callbacks/status`, in `internal/ttscallbacks` (named like the NestJS module, chosen by the user; the URL path stays `/beatrice-callbacks` because that is the contract with Beatrice and the ingress), mounted next to GraphQL (`server.Options.Routes`, which replaced `UserAdded`: the webhook of 8a is one of three routes now).

Verify: the first two groups of the `beatrice-callbacks` e2e spec pass (upload URL for a valid token, refused for a tampered one; a valid status published on the Redis channel and answered 204, a malformed one refused with 400); the unit test of the token check shows an expired token accepted and a tampered or foreign one refused.

Built as (decisions and deviations):

- **`gen-upload-url`** answers 201 `{ "url": ... }` with a PUT URL for `narrations/<jobId>.mp3` valid for 5 minutes, signed for the **cluster** endpoint (`objectstorage.Client.PresignClusterUpload`; the bucket client has two signers now), because Beatrice runs in the cluster and uploads the audio itself; only the content type (`audio/mpeg`) is signed, as the size is not known. The job ID is the `Idempotency-Key` header, which must be a UUID before it becomes part of an object key (400 otherwise). The call must carry a bearer token ZITADEL issued: `auth.IssuerCheck` checks its signature (RS256, keys of the issuer found through discovery when the backend starts, so it does not start when ZITADEL cannot be reached, like the introspection check of every other request) and its issuer, and **does not look at the expiry**: Beatrice may pick a job up long after the token of the writer who started it expired. It is a different check from the introspection that every other request goes through, which refuses an expired token. It is unit tested against a local identity provider: an expired token passes, a token signed with another key, issued by another issuer, with a changed signature or payload, or that is not a token is refused. Missing or refused token: 401 `{ "message": ... }`.
- **`status`** takes the update as Beatrice sends it (`jobId` a UUID, `status` any non-empty text, optional `progress` of at least 1, `clientContextId`, `fileSizeBytes` of at least 0, `attempt` of at least 1, `failedAt` a date, `error {code, message}`), logs it, hands it to `narration.Service.Handle` in the replica Beatrice called (8c-4: it was published to every replica in 8c-2 and 8c-3, as NestJS did) and answers 204. A malformed body is 400 with a message; a `Handle` that fails is 500, so Beatrice may try again (it does not retry today: Ponos-OS/smart-novel-beatrice#15 asks it to retry a final status and to log when it gives up). NestJS had no token check on this endpoint and neither has this one. `Status` stays Beatrice's own text: the backend acts on `completed` and `failed` only (8c-3), and an unknown one is not an error. The Redis wrapper has `Publish` now.
- **Names:** `StatusChannel` and `AudioKeyPrefix`/`AudioKey` are exported because 8c-3 reads the channel and builds the same key.
- e2e: the four tests of the first two groups of `beatrice-callbacks` pass, with the callbacks seen in the pod logs (`status callback of Beatrice`, `token of a Beatrice callback rejected` for the tampered token); the whole suite gives 326 passed and 9 failed, all in the groups of 8c-3 and 8c-4 (`beatrice-callbacks` 3, `chapter-narration` 6). An expired token cannot be tested e2e (ZITADEL's access tokens live for hours), which is why the unit test of `IssuerCheck` exists.

### Step 8c-3: Narrating a chapter

`generateChapterAudio`, the narration of a chapter that is saved, and what happens when Beatrice reports a job done. `internal/narration` (the service, its repository and the book of job progress), `internal/background`, and changes in `chapter`, `beatrice`, `auth`, `platform/redis` and `config`.

Verify: the `chapter-narration` and `beatrice-callbacks` e2e specs pass except what needs the subscription (8c-4); the pod logs show the listener started, a narration started and its audio address kept.

Built as (decisions and deviations):

- **`generateChapterAudio(id)`** (writer role, the terms guard applies, `@hasRole(role: writer)`) answers `{ status: PROCESSING, narrationURL }` at once. It refuses a chapter that does not exist (`NOT_FOUND`, which NestJS answered as a missing permission), one the viewer may not update (`FORBIDDEN`), one with no text (`BAD_REQUEST`), a chapter whose narration is running (`CONFLICT`, "already in progress"), and answers `SERVICE_UNAVAILABLE` when Beatrice cannot start the job. NestJS answered `PROCESSING` also when Beatrice failed and only logged it, which told the writer a job was running when none was; the failure is logged now as well.
- **The lock** is a Redis key `chapter_tts:<chapterID>` taken with `SET NX` for an hour at most and released with a script that deletes it only while it still holds the caller's token (`platform/redis` has `TryLock`, `Unlock`, `Subscribe`). It stays until Beatrice reports the job done. 8c-4: once Beatrice has answered, the value of the lock is swapped from the token to the job ID (`Swap`), so any replica releases it on a terminal update with the job ID; nothing about a job is in the memory of a replica.
- **Saving a chapter** (`createChapter`, and `updateContent` when the text really changed) starts a narration in the background (`internal/background.Go`: its own goroutine, the context of the request without its cancellation, a recovered panic and every error only logged), unless a narration of the chapter is running. NestJS waited for Beatrice inside the request. This is the helper the plan promised for the rule of `CONTRIBUTING.md`. `chapter.Service` calls the narration service after the save is committed, so no resolver has to remember to.
- **Beatrice's token:** the bearer token of the request goes to Beatrice with `generateAudio` and comes back on the callbacks (`auth.BearerFrom`, `beatrice.WithAuthorization`; `beatrice.HTTPClient` adds the header per request, because the generated client takes one HTTP client). Nothing logs it.
- **Beatrice answers `generateAudio` with HTTP 202 Accepted**, the GraphQL answer in the body, because the job is only queued. The generated client accepts only 200 and reported "returned error 202"; `beatrice.HTTPClient` takes 202 as the success it is (unit tested). The first run of the e2e, with every start failing and the lock released at once, showed it.
- **Handling an update** (8c-2 and 8c-3 had a listener on `tts-audio:status` in every replica, so every replica did this for every update; 8c-4 does it once, in the replica Beatrice called). For each update: an update with no chapter in `clientContextId` is dropped, one that arrives out of order is dropped (a progress no higher than the last seen is stale, and everything after a terminal update is dropped; the state is in Redis, `chapter_tts_progress:<jobID>` and `chapter_tts_ended:<jobID>`, forgotten after two hours; NestJS never forgot them), an unknown status is logged and treated as in progress, `failed` is logged, and `completed` keeps the audio address `narrations/<jobId>.mp3` on the chapter. A terminal update releases the lock of the chapter. A failure to keep the address makes `Handle` fail and forget the terminal mark, so Beatrice's next try is news. The backend acts on `completed` and `failed` only and keeps Beatrice's vocabulary as text.
- **The job is bound to its chapter** (from the automated security review): when a job starts, the lock of the chapter holds its ID (8c-3 had a second key, `chapter_tts_job:<chapterID>`, for it); the audio address is kept only when the update's job is that one, so an update nobody asked for, or about another job, cannot point a chapter at some audio, whichever replica hears it. The lock alone did not say that (a running narration of the chapter was enough). Beatrice sends `queued` while it is still answering the call that starts the job, so a job can be reported done before the code that started it has written it down (a test that reports `completed` at once did exactly that, and the lock of its chapter stayed held for its hour, as NestJS's would have). The terminal mark in Redis remembers how a job ended, and `start` finishes a job that ended already as soon as it has written it down: it keeps the audio address if it completed, and always releases the lock. What stays open, for the user: an authenticated `status` (a forged update still reaches the subscription of 8c-4, which shows progress, not audio), the audience and age of the token of `gen-upload-url`, the size of an upload (a cap needs Beatrice to upload with POST).
- `Chapter.narrationStatus`: NestJS had the field, the filter and two repository methods that wrote it, and nothing called them, so it was always null (found in 8c-4 when the user asked what NestJS did). 8c-4 writes it (decided by the user): `PROCESSING` before Beatrice is asked for a job (so a quick update cannot be overwritten by it), `FAILED` when the job cannot be started or Beatrice reports the job started for the chapter as failed, `READY` together with the audio address when it completes (one update). An update about another job changes nothing and is not announced. A narration whose job never reports stays `PROCESSING` after its lock expires an hour later (nothing sweeps it; the writer can generate again). The response of `generateChapterAudio` carries `PROCESSING`. `TtsTextService` of NestJS is not ported: nothing called it.
- Config: `BEATRICE_DEFAULT_VOICE` and `BACKEND_INTERNAL_URL` are required (NestJS validated them as required).
- e2e: `chapter-narration` (with a new case: a `completed` update of another job is not kept while the chapter's narration is running) 6 of 7 and `beatrice-callbacks` (upload URL, status, "completed persists the audio address, the narration started by saving a chapter") pass; the whole suite gives 333 passed and 3 failed, all of them the `chapterNarrationUpdated` subscription (8c-4): two of `beatrice-callbacks` and `should subscribe to chapter narration updates`; no lock is left in Redis after it. Specs renamed to the Go schema (`narrationURL`, `Time!`, "Chapter not found").

### Step 8c-4: The subscription and the audio cleanup
