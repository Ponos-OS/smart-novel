## Backend refactor, Step 1 (Taskfile replaces Nx), 2026-11-11

- `REQUIREMENTS.md` overrides the loop: the step is left uncommitted until the user approves it.
- Went well: Taskfile `includes` with `dir` and `optional: true` mapped Nx targets one to one; frontend lint (0 errors), 726 frontend tests, build, Storybook build, shared tests and 1058 backend tests pass through `task`.

- Follow-up in the same step: husky and lint-staged replaced by lefthook. The first rewrite of `pre-push` dropped its `lint:check` line; check a hook's old content before rewriting it. `core.hooksPath` was set by husky to `.husky/_` and had to be unset.
- Second follow-up: I had added `@go-task/cli` to npm and called `npx task` in CI, Dockerfiles and terraform, which contradicted the user's setup (task installed as a system tool). Replaced with `go-task/setup-task@v2` in CI and the pinned install script in the images. Before picking an install route for a tool, ask or check how the user already has it installed.
- `NODE_ENV` renamed to `APP_ENV` in the backend config, instrumentation, `.env.example`, the local `.env` and the backend Dockerfile; the frontend Dockerfile keeps `NODE_ENV` for Vite and npm.
- Security review (post-commit) caught that dropping `NODE_ENV=production` from the NestJS production image would leave Apollo introspection and stack traces on. Restored it next to `APP_ENV`. When renaming an env var, grep dependencies' behavior (not only our code) before removing the old one.

## Backend refactor, Step 4 (ent data model, Atlas migrations), 2026-11-11

- `REQUIREMENTS.md` overrides the loop: the step is left uncommitted until the user approves it. Step 3 was committed first (`41b2aaf`) on the user's go-ahead.
- Found only by the integration test against a real PostgreSQL: (1) `StorageKey` on an ent field renames the column, not the index (`UQ_writers_user` became a column); indexes are named through `index.Fields(...).StorageKey(...)`. (2) `ON DELETE RESTRICT` surfaces as SQLSTATE 23001, which `ent.IsConstraintError` does not match; the test checks the `pgconn.PgError` code. (3) ent defaults such as `time.Now` and `uuid.New` live in the application, so raw SQL inserts failed on `created_at` and `id`; `entsql.DefaultExpr("CURRENT_TIMESTAMP")` gives the columns a database default, but a database default of `gen_random_uuid()` makes `Schema.Create` emit an `ALTER ... SET DEFAULT` on every run (a quirk of how ent compares the expression), so ids have no database default, as in Prisma.
- `Schema.WriteTo` on a database built from the migration files is the drift check: it prints what ent would still change. It reported the id-default quirk above, which is how it was found. The same method gives a one-line test that a migration was forgotten.
- ent cannot express: composite foreign keys, a composite primary key whose fields are not both edges, native PostgreSQL enums without a separate Atlas setup, `CREATE EXTENSION`. All four are recorded in `REQUIREMENTS.md` step 4; the extension is a hand-written first migration written by `cmd/migrategen`.
- The edge schema (`NovelTag`) fixes the order of its composite key to the order of the two edges, so which side declares `Through` decides whether the key is `(novel_id, tag_id)` or the reverse.
- The `arigaio/atlas` image has no shell, so a Kubernetes `$(DATABASE_URL)` cannot be used (the value comes from a Secret anyway); `atlas.hcl` reads it with `getenv`. Verified: the `migrate` target applied both migrations to an empty PostgreSQL and a second run answered "No migration files to execute".
- Real stack: `start:dev` brought up the Go backend, which created the ten tables, the citext columns and the CHECK at startup; `{ health }` answered through the ingress. Not done: a second `start:dev` and `stop:dev` pair (only a backend `rollout restart`, which became ready), and `backend-e2e`.

The three older stashes were untouched. Never put `git stash` in a cleanup line; use `git stash list` to look.
- The user's own `.env` held the old `LOG_LEVEL=http` and `LOG_MODE`, which the Go config rejects. I changed those two keys and added `DEV_SYNC_DATABASE_SCHEMA=true` (backup in the session scratchpad) so the stack could start. A rename of an env key needs a note for existing `.env` files.
